# System Design Write-up

## Slot hold mechanism

Booking is two steps, not one. `POST /appointments/hold` reserves a slot by creating an `Appointment` row with `status: HELD` and `holdExpiresAt` set `BOOKING_HOLD_MINUTES` (default 5) in the future. The patient then fills in symptoms and calls `POST /appointments/:id/confirm`, which requires the hold to still be unexpired and flips the row to `CONFIRMED`. This gives the patient a window to fill out the symptom form without another patient grabbing the same slot mid-flow, while keeping the reservation itself short-lived so an abandoned booking doesn't lock a slot indefinitely.

Expiry is enforced lazily rather than by a background sweep: `confirmAppointment` checks `holdExpiresAt` against `now()` and rejects (410, "hold expired") if it's passed, flipping the row to `EXPIRED`. On the write side, `holdSlot` first runs an `updateMany` that flips any stale `HELD` row for that exact doctor+slot to `EXPIRED` before attempting its own insert, so an abandoned hold doesn't permanently block the slot for other patients — the next person to try that slot clears it. The slot-listing query (`getAvailableSlots`) also excludes `HELD` rows whose `holdExpiresAt` has passed, so a stale hold never shows as unavailable even before it's formally swept. No periodic cron sweeper is needed for correctness — only slots someone actually revisits need to be freed, and lazy sweep-on-write handles exactly that.

## Double-booking prevention

This is enforced at the database layer, not in application code. `Appointment` has a partial unique index — `UNIQUE (doctorId, slotStart) WHERE status IN ('HELD', 'CONFIRMED')` — added as a raw-SQL migration since Prisma's schema DSL doesn't express partial indexes. The application never does a "check availability, then insert" sequence, which would race under concurrent requests; it always just *attempts* the insert inside a transaction and lets Postgres reject a conflicting one atomically. A unique-violation (`P2002`) is caught and turned into a 409 response. Two patients hitting "hold" for the same slot at the same instant cannot both succeed — one wins, the DB itself decides which, and there's no window for a race regardless of how many app server instances are running. This is verified by an automated test (`backend/tests/booking.concurrency.test.js`) that fires 5 concurrent hold requests at the same doctor+slot against a real Postgres instance and asserts exactly one returns 201.

## Doctor leave conflict handling

When an admin calls `POST /admin/doctors/:id/leave`, `addLeave` runs everything in one transaction: it inserts the `DoctorLeave` row, finds every `HELD`/`CONFIRMED` appointment for that doctor on that date, flips each to `CANCELLED_BY_LEAVE`, and writes one `NotificationLog` row per affected patient (email) plus one `CALENDAR` delete row per party. Because this is one transaction, a leave day is never recorded without its cancellations, and vice versa — there's no window where the leave exists but a patient still holds a now-invalid confirmed slot. The endpoint returns `cancelledCount` so the admin UI can immediately show how many patients were affected. Slot generation and the leave-day check in `holdSlot` both consult `DoctorLeave` directly, so once a leave day is recorded no new booking can land on it either.

## Notification failure handling

Every outbound side-effect — booking confirmation email, cancellation email, leave-cancellation email, post-visit-ready email, medication reminder email, and each Calendar create/update/delete — is represented the same way: a `NotificationLog` row with `type` (`EMAIL`/`CALENDAR`), a `payload` describing what to do, and a `status` (`PENDING`/`SENT`/`FAILED`) with a `retryCount`. Nothing sends synchronously inline with the request that triggered it; the row is written inside the same transaction as the state change (booking confirm, cancellation, leave processing), so the notification is never lost even if the send fails later.

A single cron job (`NOTIFICATION_POLL_CRON`, default every minute) drains `PENDING`/`FAILED` rows under `NOTIFICATION_MAX_RETRIES`, dispatches each to either the email sender or the Calendar sync function based on `type`, and marks it `SENT` on success or bumps `retryCount`/`lastError` on failure — one retry mechanism covers every notification type instead of each caller reimplementing its own. A user who hasn't connected Google Calendar isn't a failure case: the sync function detects the missing OAuth token and returns immediately, and the row is marked `SENT` (nothing to do) rather than retried forever. The interval between poll ticks is itself the backoff — no separate exponential-delay bookkeeping is needed at this scale, though it would be a straightforward addition (respect `updatedAt` + `retryCount` before re-attempting) if send volume grew.

## Scope notes

Reschedule is implemented as cancel-then-rebook rather than a dedicated atomic endpoint — this still satisfies "calendar event updated or deleted on reschedule" (delete fires on cancel, create fires on the new confirm) while reusing the existing hold/confirm/cancel machinery instead of adding a third state-transition path. All scheduling math is UTC-based; a production deployment would pin working hours to the clinic's timezone explicitly.
